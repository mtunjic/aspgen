The insight

02 Architecture should be a commodity, not a craft project

Clean Architecture, DDD, and CQRS aren't controversial anymore — they're well-understood, well-documented patterns. What's still expensive is hand-typing them correctly, consistently, every single time.

aspgen treats proven architecture patterns the way modern tooling treats formatting or linting: something a machine enforces perfectly, every time, so people can spend their time on the 20% that's actually unique to the business.

$ git clone your-new-service
// old way: 2-3 weeks of scaffolding
 
$ aspgen new Billing --context Billing --arch es
✓ Solution, layers, tests, CI — generated.
// new way: under a minute

The solution

03 aspgen: one CLI, real code, every layer

A single Go binary that renders idiomatic, human-readable C#/XAML from proven templates — no black box, no runtime dependency, no vendor lock-in. What you get out is code your own team fully owns from line one.

🏗️Real layers

Domain, Application, Infrastructure, WebApi — properly separated, properly dependency-inverted, every time.

🧠Real DDD

Aggregate roots, value objects, domain services, domain events, repositories — the actual building blocks, not a diagram.

🔀Real CQRS

Vertical-slice commands and queries, one handler per verb, thin endpoints — not a shared "God service."

📜Real Event Sourcing

An append-only event store, replayable aggregates, and live read-model projections — full audit trail, out of the box.

How it works

04 Two verbs. That's the whole workflow.

1new

Bootstrap a solution once — tree, project layout, CI script, and a manifest that remembers everything you've built.

2add

Incrementally grow it — entities, aggregates, repositories, events, whole UI frameworks — safely, idempotently, forever.

3own it

Nothing calls home. Nothing re-downloads. What's generated is yours — customize the templates themselves for your house style.

No wizard UI to fight, no cloud service to trust, no proprietary DSL to learn — just a CLI and real source files.
